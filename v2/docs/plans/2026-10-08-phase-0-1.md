**Phase 0 — Foundations**
1. **Scaffold** `v2/`: workspaces, `tsconfig.base.json`, `docker-compose.yml` (Postgres 16), root scripts `dev | test | build | fresh | e2e`. *Test:* each workspace's smoke test passes and `npm run build` is clean.
2. **`domain/money.ts`**: integer cents, plus `allocate(total, weights)` using largest remainder. *Test:* the parts always sum to the total; value and qty bases; zero weights are rejected.
3. **`domain/avco.ts`**: `receive`, `issue` (the last unit drains the remainder), `revalue`. *Test:* the guide's $550 example; the pool drains to exactly 0.
4. **`domain/landed.ts`**: `landedCost(lines, freight, basis)` and `splitAdjustment(amount, ordered, received, remainingOnHand)` → inbound / onHand / sold. *Test:* 2×$500 + $100 gives $550 per unit and $1,100 total; mixed lines; the split sums exactly.
5. **`domain/posting.ts`**: event → role lines, plus `assertBalanced`. *Test:* **golden tests for every purchase-side and opening-balance example in the GAAP guide.**
6. **`domain/status.ts`**: the three PO axes, plus the bill, receipt and scan-session machines. *Test:* every legal transition works and every illegal one is refused.
7. **`api` Prisma core**: Company, Profile, Account (with parent), PostingRule + Change, JournalEntry/Line, AuditEvent; migration; a test harness (fresh schema per test file on real Postgres, `app.inject`). *Test:* the migration applies and `/health` responds.
8. **`api/ledger.ts`**: `postEntry(tx, event, amounts, ref)` resolves rules and enforces balance; `reverse()`; boot seeds the GAAP chart and rules without ever overwriting edits. *Test:* an unbalanced entry is refused; a locked control account can't be repointed; a reversal nets to zero.
9. **`api/books.ts`** `checkBooks()` + test helper `expectBooksSound()`: TB balanced; 1201 = Σ pools; 1202 = open inbound; held units valued at 0. *Test:* a planted mismatch is detected (prove the check can fail).
10. **`api` access**: profile picker (`X-Profile` header, no passcode), with audit stamping. *Test:* the actor is recorded; an unknown profile is rejected.
11. **`api` setup**:
    - `GET /setup` state; step endpoints; `setupCompletedAt`.
    - **Sample-data loader:** 1 warehouse, a supplier and a carrier, 3 items (regular w/ UPC, serial, open-box variant), 0 stock, 0 transactions.
    - "Clear sample data", refused once any entry has posted.
    - `npm run fresh`.

    *Test:* a fresh DB reports setup required; the sample counts are exact; clear is refused after a posting.
12. **`web` shell**: PWA manifest and service worker; Mantine theme porting the ProfitIndex tokens (the `--surface / --ink / --signal / --text-*` set from `frontend/src/theme.css:20-88,149-185`, light and dark); router; profile picker; Clerk / Accounting / Admin home screens. *Test:* Playwright smoke at 390px and 1440px; the manifest is installable; a port of `backend/test/theme-contract.test.ts` (AA contrast and light/dark token parity).
13. **`web` setup wizard**: 8 resumable steps with CSV import (vendors, items, opening stock), plus the **printable test sheet** page (sample barcodes, serial labels, packing slip). *E2E:* fresh → wizard → sample data → home.

**Phase 1 — Scan-to-bill**
14. **Items, barcodes, vendors, warehouses**: CRUD and CSV; `GET /items/by-code/:code` with GTIN normalization (UPC-A ↔ EAN-13 ↔ GTIN-14, vendor SKU). *Test:* a UPC scan finds an item registered by EAN; a duplicate code returns 409.
15. **`api/stock.ts`** is the only balance mutator: `hold`, `releaseHeld`, `receiveOnHand`, `issue`. Pools, lots and versions are optimistic, and a lost race returns **409**. *Test:* held stock is never available; concurrent receive and issue both apply.
16. **Opening stock** (setup step 7): Dr 1201 / Cr 3000. *Test:* the books stay sound.
17. **Purchase orders**: manual create and edit, three axes, no GL. *Test:* editable until billed; the axes derive correctly.
18. **Scan sessions**: open, append events (idempotent by UUID), adjust counts, submit (atomic claim). *Test:* a replayed UUID is a no-op; a double submit returns 409.
19. **Matcher on submit**: the three branches (billed PO / unbilled PO / no PO) plus extras and overs to a new PO. *Test:* one scenario per branch, with `expectBooksSound()`.
20. **Draft bill editing + `GET /bills/:id/preview`**: vendor, invoice #, dates, terms → due date, lines, per-line discount, freight-on-bill, basis, attachment. *Test:* the preview equals what posting books, to the cent.
21. **Post bill**: GL entry, auto-post of pending receipts (held → on hand, pools, lots), PO axes. Partial receipts clear 1202 with the telescoping `clearedAt(n)` pattern ported from `backend/src/goods_receipt.ts:108-119`, so the last unit clears exactly what is left. *Test:* the guide examples end to end; telescoping partial receipts; books sound.
22. **Receipts against a billed PO** (scan or manual), including serial units. *Test:* over-receipt goes to extras; a duplicate serial returns 409.
23. **Freight-In bills + allocation**. *Test:* freight posted before receipt, after receipt, and after a partial sale (the sold share goes to COGS); books sound.
24. **Vendor credits**: purchase return (received / not received) and a price discount on one line. *Test:* guide #3, #4, #6, #7, #8.
25. **Payments**: partial payments and refunds, payment axis, AP aging by due date. *Test:* guide #5; refund after a return; overpaying is refused.
26. **Void bill** rules. *Test:* refused after any receipt or payment.
27. **Reports API**: trial balance, valuation vs GL, held-awaiting-bill aging, AP aging. *Test:* figures match the scenario fixtures.
28. **Claude reader** (`/ai/read-slip`, `/ai/read-label`): zod schema, refusal fallback, graceful degrade, mapping to items via vendor SKU and barcode. *Test:* a mocked client covers the mapping; an API error yields `{available:false}`; an optional live eval behind `RUN_AI_EVAL=1`.
29. **Web scanner**:
    - zxing-wasm in a Web Worker, with a native `BarcodeDetector` fast path.
    - Continuous scanning, with the same code de-duped within 1.5s.
    - Torch, haptics and sound; green/amber/grey states.
    - Practice mode.

    *E2E:* the fake camera video produces 3 reads. The fixture `e2e/fixtures/make-video.ts` renders the sample barcodes with `zxing-wasm/writer` (the same library the printable test sheet uses, so no second barcode dependency) and turns them into a `.y4m` with ffmpeg, which is available in this container.
30. **Receive-delivery wizard** (5 steps) with an offline queue (Dexie) and a sync badge. *E2E:* scans made offline sync after reconnect; the clerk at 390px gets "waiting for accounting".
31. **Bill desk**: inbox, review wizard, live landed preview (domain package), post; card layout below `sm`. *E2E:* edit cost, add freight, post → stock live at the landed cost.
32. **Freight bill wizard + Payables** (aging, pay, refund, credits). *E2E.*
33. **Coaching + Getting-started checklists + Reports pages.** *E2E:* full cycle from a fresh install, then the books reconcile via the API.
34. **Docs + packaging**: `v2/README.md` (run, fresh install, test, deploy), a `v2/Dockerfile` (single image: API serving the built PWA), and `v2/docker-compose.yml` (app + Postgres) that runs on any host. **No Render dependency** (user, 2026-10-08).

## Verification
- **Unit:** `npm test -w packages/domain` covers every GAAP-guide journal example as a golden test, plus AVCO and allocation property tests (sum of allocations == freight; pool never negative).
- **API:** `npm test -w apps/api` runs against real Postgres (docker compose service). It covers scenario tests for each event in the posting table, with the four invariants asserted after each, plus idempotent scan replay, the double-submit 409, and hold → post landing.
- **E2E:** `npm run e2e` (Playwright, Chromium with `--use-fake-device-for-media-stream --use-file-for-fake-video-capture=<barcodes>.y4m`) covers:
  1. fresh install → setup wizard → sample data
  2. clerk scans 3 barcodes on a 390px viewport → submit
  3. accounting edits the draft bill, adds freight, posts
  4. stock is live at the landed cost
  5. pay
  6. trial balance + valuation reconcile
- **Manual:** `npm run fresh && npm run dev`, then check on a real phone (HTTPS tunnel), light and dark, 390px and 1440px.
- `npm run build` (typecheck) is clean.
